CC Order Tracking System — Admin Frontend

Administrative dashboard for managing computer repair orders.

Overview

The Admin Frontend is a static single-page application that provides an administrative dashboard for managing computer repair orders. Admins can create orders, add repairs, update statuses and costs, and close completed repairs — all from a single interface.

Built with vanilla JavaScript (ES modules), BeerCSS 4.0 (Material Design 3 CSS framework), Material Icons, and Material Dynamic Colors (Material You theming). No build step, bundler, or framework required.

Getting Started

Prerequisites

  • Any static file server (e.g. npx serve, python3 -m http.server)
  • Backend running at http://localhost:8000 (configurable in js/api.js)

Setup

  1. Serve the directory 
    npx serve front-end/Admin/
# or
python3 -m http.server 8080 --directory front-end/Admin/
  2. Ensure the backend is running on http://localhost:8000.
  3. Open http://localhost:8080 in a browser.

The app requires no build step. Just serve the static files.

  ],

Module: theme.js

Manages dark/light/auto theme mode using BeerCSS's built-in theming API with Material Dynamic Colors.

Exports

ExportDescription
initTheme()Initialises the theme in 'auto' mode with primary colour #f3d998
toggleTheme()Toggles between 'dark' and 'light' modes

Behaviour

  1. initTheme() calls BeerCSS ui('mode', 'auto') — follows system preference initially.
  2. Primary theme colour is #f3d998 (warm amber/yellow), passed to Material Dynamic Colors.
  3. toggleTheme() flips between 'dark' and 'light' via BeerCSS's ui('mode', ...).
  4. The toggle icon updates between dark_mode and light_mode Material Icons on both sidebar and bottom nav buttons.

Views

Dashboard

The landing view showing a high-level overview of all repairs:

  • 4 Stat Cards — Total Repairs, Open / In Queue (orange), In Progress (blue), Completed (green). Each card has a Material Icon and colour-coded icon wrap.
  • Recent Repairs Table — The 5 most recent repairs sorted by finish date (then creation date). Shows Customer, Device, Cost, Status (colour chip), ETA, and Action buttons (Edit / Close).
  • Last updated timestamp below the heading.
  • View All button navigates to the Orders view.

Orders

The full order management view:

  • Search bar — Filters repairs in real-time (debounced 250ms) by customer name, device, repair ID, order ID, or status.
  • Filter chips — 5 chips (All, Open, In Progress, Completed, Closed) with live counts. Selected chip has a filled colour.
  • Order groups — Repairs grouped by order_id in accordion-style cards. Each header shows the short order ID, customer name, repair count, and an "Add Repair" button (hidden if all repairs are Closed). Clicking the header toggles the table body.
  • Repair table — Columns: Repair ID (short), Customer, Device, Cost, Status (colour chip), ETA, Start, Finish, Actions (Edit / Close).
  • Empty state — Shown when no repairs match the current filter or search.

Data Flow

The app follows a fetch → render → act → re-fetch pattern for all CRUD operations.

Create Order

User fills form -> handleCreate()
  +-- Validates customer name + all repair rows
  +-- POST /admin/createorders  (apiCreateBulkRepairs)
  +-- Closes dialog
  +-- loadData() -> re-render everything

Update Repair

User clicks Edit -> openEditDialog(repairId)
  +-- Pre-fills cost + ETA from existing repair
  +-- User saves -> handleEdit()
       +-- PUT /admin/updateorder/{order_id} (apiUpdateRepair)
       +-- Closes dialog
       +-- loadData() -> re-render

Close Repair

User clicks Close -> openCloseDialog(repairId)
  +-- Shows confirmation with device/customer/status
  +-- User confirms -> handleClose()
       +-- PUT /admin/closeorder/{order_id} (apiCloseRepair)
       +-- Closes dialog
       +-- loadData() -> re-render

Add Repair to Order

User clicks "Add Repair" on order card -> openAddRepairDialog(orderId)
  +-- Shows order ID + customer name
  +-- User saves -> handleAddRepair()
       +-- POST /admin/addrepair/{order_id} (apiAddRepair)
       +-- Closes dialog
       +-- loadData() -> re-render

Customization

API Base URL

Edit js/api.js to point to a different backend:

export const API_BASE = 'https://api.example.com';

Theme Colour

Change the primary colour in js/theme.js:

ui('theme', '#your-color-here');

Status Values

Status constants and predicates are defined in js/render.js:

const STATUS_OPEN = 'Picked-up';
const STATUS_IN_PROGRESS = 'Work in progress';
const STATUS_PARTS = 'Picking up parts';
const STATUS_FINISHED = 'Finished';
const STATUS_CLOSED = 'Closed';

Edit these constants and the corresponding isOpen(), isInProgress(), isComplete(), isClosed() predicates to customise the workflow.

Colour Mapping

Status-to-colour mapping is handled by getStatusColor() in js/render.js. Add new keyword checks to extend colour support for additional statuses.

BeerCSS Framework

The app uses BeerCSS 4.0.21 loaded from CDN. All Material Design 3 components (cards, chips, dialogs, tables, nav) are available. Refer to beercss.com for documentation.

Backend Status Normalisation

The backend business_logic.py maps raw database statuses to repair_status_display. New status mappings can be added on the backend without modifying the frontend.
