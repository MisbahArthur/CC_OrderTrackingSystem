CC Order Tracking System — Database

PostgreSQL 16 — reliable, ACID-compliant storage layer.

Overview

The database layer for the CC Order Tracking System uses PostgreSQL 16 to store and manage repair order data. PostgreSQL provides ACID compliance, robust data integrity, and strong consistency — well-suited for an order-tracking workload.

The database runs inside a Docker container managed by Docker Compose. The schema is initialised automatically via SQLAlchemy's Base.metadata.create_all() on backend startup, with an optional init script for manual setup.

Getting Started

Prerequisites

  • Docker & Docker Compose installed

Setup

  1. Start the database 
    cd db
docker compose up -d
  2. Verify the container is healthy 
    docker compose ps

    Wait until postgres_node shows healthy in the status column. The init container (postgres_init) will run automatically after health checks pass.

  3. Verify the schema was loaded 
    docker exec postgres_node psql -U postgres -d CC_Ordertracking -c "\dt"
docker exec postgres_node psql -U postgres -d CC_Ordertracking -c "SELECT * FROM order_tracking LIMIT 5;"

Table: order_tracking

Creation SQL:

CREATE TABLE IF NOT EXISTS order_tracking (
    order_id UUID NOT NULL,
    repair_id UUID NOT NULL,
    customer_name VARCHAR,
    repair_device VARCHAR,
    repair_cost NUMERIC,
    repair_start TIMESTAMP,
    repair_finish TIMESTAMP,
    repair_status VARCHAR,
    repair_eta VARCHAR,
    PRIMARY KEY (order_id, repair_id)
);

Primary Key Design

Composite Primary Key: (order_id, repair_id)

Orders are identified by order_id and may contain multiple repairs. The composite primary key ensures each repair within an order is uniquely addressable. Queries filtering by order_id use a standard B-tree index on the primary key.

Trade-offs:

  • Listing all orders across all rows is efficient via a full table scan or a covering index.
  • Cross-order queries (e.g. "all repairs for customer X") can be supported by the index on customer_name.
  • repair_status is not indexed — status-based filtering across orders may require a full scan. Add an index if this becomes a bottleneck.

Status transitions are enforced by the backend business logic, not by database constraints. The database stores the raw status string as-is.

Data Flow

Startup Sequence

  1. Docker Compose starts the postgres container.
  2. PostgreSQL initialises its data directory, creates the CC_Ordertracking database (via POSTGRES_DB env var).
  3. The health check polls every 10s until pg_isready succeeds.
  4. Once healthy, Docker Compose starts the db-init container, which executes init.sql against the postgres host.
  5. The init container exits. The postgres container remains running.

Application Interaction

  1. When the backend starts, main.py calls Base.metadata.create_all(bind=engine), which creates the order_tracking table if it does not exist.
  2. Route handlers inject a SQLAlchemy Session via the FastAPI dependency get_database().
  3. All queries use SQLAlchemy ORM methods, preventing SQL injection.
  4. On FastAPI shutdown, sessions are closed automatically via the dependency's finally block.
