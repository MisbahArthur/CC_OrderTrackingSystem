CC Order Tracking System — Database

Apache Cassandra 5.0.7 — durable, scalable storage layer.

Overview

The database layer for the CC Order Tracking System uses Apache Cassandra 5.0.7 to store and manage repair order data. Cassandra provides high availability, linear scalability, and fault tolerance — suitable for a production order-tracking workload.

The database runs inside a Docker container managed by Docker Compose. The schema is initialised automatically on first startup via a dedicated init container that executes a CQL script.

Getting Started

Prerequisites

  • Docker & Docker Compose installed

Setup

  1. Start the database 
    cd db
docker compose up -d
  2. Verify the container is healthy 
    docker compose ps

    Wait until cassandra_node shows healthy in the status column. The init container (cassandra_init_script) will run automatically after health checks pass.

  3. Verify the schema was loaded 
    docker exec cassandra_node cqlsh -e "
  USE order_keyspace;
  DESCRIBE TABLES;
  SELECT * FROM order_tracking LIMIT 5;
"

Creation CQL:

CREATE TABLE IF NOT EXISTS order_tracking (
    order_id UUID,
    repair_id TIMEUUID,
    customer_name text,
    repair_device text,
    order_creation TIMEUUID,
    repair_cost decimal,
    repair_start timestamp,
    repair_finish timestamp,
    repair_status text,
    repair_eta text,
    PRIMARY KEY (order_id, repair_id)
) WITH CLUSTERING ORDER BY (repair_id ASC);

Primary Key Design

Partition Key: order_id

A single order is stored as one Cassandra partition. All repairs belonging to the same order reside in the same partition, enabling efficient single-order queries. Queries filtering by order_id hit exactly one partition.

Clustering Key: repair_id ASC

Within a partition, rows are ordered by repair_id in ascending order. Since repair_id is a TIMEUUID, rows are naturally sorted by creation time — the oldest repair appears first.

Trade-offs:

  • Listing all orders across all partitions requires a full table scan (no ALLOW FILTERING needed for SELECT *).
  • Cross-order queries (e.g. "all repairs for customer X") are not natively supported and would require a secondary index or materialised view.
  • The repair_status field is not indexed — status-based filtering across orders requires scanning.

UUID Generation

The backend generates three types of UUIDs for different purposes:

FieldUUID TypeGenerationPurpose
order_idUUIDv4 (random)uuid.uuid4()Unpredictable partition key; prevents partition hot-spotting
repair_idUUIDv1 (time-based)uuid.uuid1()Enables time-ordered clustering within a partition
order_creationUUIDv1 (time-based)uuid.uuid1()Captures the creation timestamp in a sortable format

Data Flow

Startup Sequence

  1. Docker Compose starts the cassandra container.
  2. Cassandra initialises its cluster, datacenter, and internal tables.
  3. The health check polls every 10s until cqlsh -e 'describe keyspaces' succeeds.
  4. Once healthy, Docker Compose starts the cassandra-init container, which executes init.cql against the cassandra_node host.
  5. init.cql creates order_keyspace (if not exists) and order_tracking (if not exists).
  6. The init container exits. The cassandra container remains running.

Application Interaction

  1. The backend CassandraManager.connect() is called during FastAPI startup.
  2. It creates a Cluster connection and sets the keyspace on the session.
  3. Route handlers inject the session via the FastAPI dependency get_cassandra_session().
  4. All queries use parameterised %s placeholders to prevent CQL injection.
  5. On FastAPI shutdown, CassandraManager.close() shuts down the cluster connection gracefully.
